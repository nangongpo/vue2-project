# backend 安全与功能需求基线

本文档回答“系统必须做到什么”。它是需求和验收基线，不重复定义权限码、审批字段、租户表结构、文件扫描命令或数据库运维步骤。详细规则分别见：

- [租户安全设计](TENANCY_SECURITY.md)
- [权限体系](PERMISSION_DESIGN.md)
- [权限码规范](PERMISSION_CODE_STANDARD.md)
- [审批契约](APPROVAL_CONTRACT.md)
- [文件安全设计](FILE_SECURITY.md)
- [配置说明](CONFIGURATION.md)

## 1. 合规边界

系统按“默认拒绝、最小权限、职责分离、后端强制、可追溯、可恢复”建设，覆盖以下等保控制目标：

- 身份鉴别、账户生命周期、认证器保护和会话安全；
- 访问控制、权限分层、数据范围、租户隔离和管理职责分离；
- 安全审计、日志完整性、集中留存、备份恢复和告警；
- 通信保护、敏感数据保护、恶意代码防范和安全运维；
- 安全开发、变更控制、漏洞修复和上线验收。

参考 GB/T 22239-2019、GB/T 25070-2019、GB/T 28448-2019 及组织适用的密码和数据安全要求。本文档不是定级、测评或认证结论；生产环境必须提供配置和演练证据。

## 2. 运行环境要求

执行开发、构建、Prisma、NestJS 和测试命令前必须：

```bash
nvm use
node --version
pnpm --version
```

版本以仓库 `.nvmrc` 和 `package.json` 中较高要求为准。环境不一致时不得以“本机可以运行”作为验收依据。

## 3. 必须满足的安全要求

### 3.1 身份与会话

- 用户必须使用唯一账号；禁用、过期、锁定或删除状态的账号不得登录和调用业务接口。
- 密码必须使用有界成本的强哈希保存；不得保存明文、可逆密码或在日志中输出密码。
- 管理员和高风险操作必须使用 MFA；MFA 密钥加密保存，重置必须走审批或受控应急工单。
- 登录失败、验证码、密码重置和敏感接口必须有独立限流、锁定和告警策略。
- Cookie 会话必须使用 `HttpOnly`、`SameSite`、生产 HTTPS 和 CSRF 防护；会话必须支持绝对过期、空闲过期、并发上限和主动吊销。
- 登录、登出、MFA、密码、会话吊销和认证失败都必须记录安全审计事件。

### 3.2 授权与职责分离

- 页面、按钮、API、字段、管理权限和数据范围必须独立显式授权；前端隐藏不能替代后端鉴权。
- 权限判定采用拒绝优先：用户、会话、角色、授权关系、权限资源、方法/路径、租户上下文和数据范围均有效时才允许。
- 权限、角色、页面、按钮、接口或数据范围被禁用、撤销或过期后，既有会话必须立即失效或重新计算权限。
- 系统管理员、安全管理员、审计管理员和业务角色必须按职责分离；不得由同一账号闭环完成高危授权、执行和审计复核。
- 高危角色、权限、数据范围、接口路由、MFA 重置、文件高危操作和审计策略变更必须经过申请、审批、执行、复核。
- 授权、回收、审批和应急操作必须支持幂等、并发冲突保护、目标受益人限制和完整审计。

完整判定模型和角色职责见 [PERMISSION_DESIGN.md](PERMISSION_DESIGN.md)，高危审批接口见 [APPROVAL_CONTRACT.md](APPROVAL_CONTRACT.md)。

### 3.3 单租户与多租户

- 单租户模式也必须创建并使用明确的默认租户，禁止用 `NULL`、隐式公共数据或客户端参数代替租户边界。
- 多租户模式下每个请求必须绑定服务端会话中的有效租户上下文；租户标识不得信任请求体、查询参数或前端路由。
- 用户、角色、权限、组织、部门、文件、审批、审计和业务数据必须具有明确的租户归属或明确的全局数据分类。
- 组织和部门数据范围必须在租户内闭合；跨租户授权、查询、下载、审批和导出默认拒绝。
- 单租户与多租户切换必须经过备份、预检、迁移、灰度、回滚和审计，不允许通过临时兼容分支绕过统一模型。

详见 [TENANCY_SECURITY.md](TENANCY_SECURITY.md)。

### 3.4 文件与恶意代码

- 上传对象必须先进入隔离区，完成大小、分片、哈希、类型和策略校验，并通过 ClamAV 扫描后才可进入可用状态。
- 隔离、扫描中、扫描失败、病毒命中、拒绝、删除和恢复状态必须明确；扫描不可用不得放行文件。
- 文件存储不得位于前端静态目录、Git 目录或可直接猜测的 URL；下载必须重新鉴权、校验租户/数据范围并使用短期地址或受控流。
- 原始文件名、MIME、扩展名和客户端哈希均为不可信输入；文件名展示、路径拼接和内容处理必须防止注入、路径穿越和类型混淆。
- 删除、拒绝、恢复、重新扫描等高危动作必须记录原因、操作者、来源、前后状态和扫描结果。

详见 [FILE_SECURITY.md](FILE_SECURITY.md)；ClamAV 运维见 [CLAMAV_CONFIGURATION.md](CLAMAV_CONFIGURATION.md)。

### 3.5 审计与证据

审计事件至少包含：操作者、目标租户、目标资源、动作、结果、时间、traceId、来源地址、前后摘要和失败原因。密码、MFA 密钥、验证码、会话令牌、连接串和对象存储凭据不得进入日志。

生产环境还必须具备：

- 独立或集中只追加存储，业务账号无权修改历史审计；
- 完整性校验、传输保护、时间同步和校验失败告警；
- 与生产权限隔离的备份、恢复演练和保留策略；
- 容量、写入失败、采集链路中断和安全事件告警；
- 审计查询、导出、备份恢复和策略变更自身可追溯。

没有部署配置、权限清单、演练记录和告警证据，不得仅凭代码或数据库表声明满足等保审计要求。

## 4. 接口与数据约束

- 统一使用 `/api/v1` 前缀、稳定的驼峰 JSON 字段和统一错误结构；不得把内部异常、SQL、文件路径或密钥返回给客户端。
- DTO 必须执行类型、长度、格式、枚举、分页、排序和业务状态校验；不能把客户端传入的租户、用户、拥有者字段直接作为授权依据。
- 列表、详情、导出、下载、选项和批量接口必须分别执行权限、字段和数据范围校验；不能因列表已授权而自动开放详情或导出。
- 删除优先采用逻辑删除或受保护状态转换；有引用、审批中、审计关联或合规保留要求时不得物理删除。
- 写操作必须具备事务、一致性、幂等或并发冲突策略；状态转换必须由服务端定义，禁止客户端直接写入任意状态。

## 5. 验收矩阵

| 控制域 | 最低验收要求 | 必须留存的证据 |
| --- | --- | --- |
| 身份鉴别 | 密码、MFA、锁定、会话过期、吊销和 CSRF 正反向测试 | 测试报告、配置和安全日志 |
| 访问控制 | 未授权、越权、跨租户、跨组织、字段和导出拒绝 | HTTP 测试、权限矩阵、审计记录 |
| 职责分离 | 高危角色互斥，申请/审批/执行/复核不可闭环 | 角色矩阵、审批记录、冲突测试 |
| 文件安全 | 隔离、扫描失败不放行、病毒命中拒绝、下载重鉴权 | 扫描记录、EICAR 演练、下载测试 |
| 审计 | 关键成功/失败事件、脱敏、完整性、查询和导出可追溯 | 日志样本、校验失败演练、权限清单 |
| 备份恢复 | 数据库和审计数据备份、恢复点、恢复时长和权限隔离 | 备份任务、恢复演练报告 |
| 运维安全 | 迁移、密钥轮换、应急工单、回滚和告警流程可执行 | 工单、变更单、告警和回滚记录 |

## 6. 当前工程状态与边界

工程验证结果应由 CI、发布验收记录和部署证据库维护，不把一次性验证快照作为当前状态依据。以下事项必须在生产上线前另行完成并留存证据：

- 真实部署环境的集中审计存储、完整性保护、保留、备份恢复、容量告警和时钟同步；
- 真实 MySQL、Redis、ClamAV、对象存储或文件盘的权限隔离、TLS、故障和恢复演练；
- 所有未来业务仓储接入统一租户、组织、部门和数据范围守卫；
- 真实浏览器、反向代理、HTTPS、Cookie、CSRF、MFA 认证器和灾备场景验收；
- 渗透测试、漏洞扫描、供应链检查、密钥轮换和等保测评机构要求的补充材料。

工程测试通过不等于系统已通过等保测评；任何未完成控制点必须记录在发布风险和整改计划中，不能通过删除测试或放宽拒绝策略“解决”。
