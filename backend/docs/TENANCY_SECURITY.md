# 单租户与多租户安全切换设计

## 1. 文档定位

本文档定义系统在单租户模式和多租户模式之间安全运行、迁移和切换的目标架构，覆盖租户、组织、部门、用户、角色、数据范围、文件模块、会话、审批、审计、备份恢复和验收。

本文档以等保三级及高安全场景为设计基线，参考现行的 GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》、GB/T 25070-2019《信息安全技术 网络安全等级保护安全设计技术要求》和 GB/T 28448-2019《信息安全技术 网络安全等级保护测评要求》。三个标准在全国标准信息公共服务平台显示为现行；最终定级、密码应用、数据分类分级、留存期限和测评结论以组织定级备案、适用法律法规、密码管理要求和测评机构意见为准。

单租户不是关闭租户隔离，多租户也不是允许客户端自行选择数据范围。两种模式必须使用同一套服务端租户边界和拒绝优先的授权模型。

## 2. 安全目标

1. 任意业务数据必须归属且只能归属一个有效租户。
2. 空租户、禁用租户、租户上下文不确定时默认拒绝。
3. 客户端提交的 `tenantId`、组织、部门和数据范围只作为候选输入，不能直接成为授权依据。
4. 单租户模式可以简化业务交互，但不能绕过数据库过滤、对象存储隔离、权限校验或审计。
5. 多租户切换必须绑定登录会话、用户成员关系、角色、数据范围和审计链。
6. 模式切换必须是受控变更，不能通过普通配置热修改或前端按钮即时改变。
7. 文件、任务、审批、审计和缓存都必须带租户边界；任何跨租户引用默认失败。
8. 权限、数据范围、组织层级和租户状态变更必须可追溯、可回滚、可复核。
9. 数据库成功而缓存、对象或审计失败时不得放大权限；系统应保持拒绝状态。
10. 故障、恢复、迁移和重放场景不能导致跨租户数据泄露。

## 3. 术语与边界

### 3.1 租户

租户是业务数据隔离、安全策略、组织树、用户成员关系和配额的一级边界。租户状态至少包括：

```text
ACTIVE       可登录、可读写
SUSPENDED    保留数据，禁止业务写入和文件下载
DISABLED     禁止访问，等待清理或归档
DELETED      逻辑删除，禁止恢复为 ACTIVE，恢复须走受控流程
```

### 3.2 组织与部门

组织和部门是租户内的层级主数据：

```text
Tenant
└── Organization
    └── Department
        └── User membership
```

组织、部门、用户归属和父子关系不能跨租户。组织是业务边界，部门是组织内的人员和数据范围边界；两者不能仅凭名称或客户端 ID 判断归属。

### 3.3 当前租户上下文

当前租户上下文由服务端从已认证会话中确定，至少包含：

```text
tenantId
tenantStatus
userId
membershipId
roleVersion
dataScopeVersion
authenticatedAt
reauthenticatedAt
```

请求头、查询参数、路由参数和请求体中的租户字段不能覆盖会话上下文。

## 4. 模式定义

### 4.1 模式配置

模式是部署级安全配置，不是普通业务用户可以修改的设置：

```dotenv
TENANCY_MODE=SINGLE
DEFAULT_TENANT_CODE=default-tenant
DEFAULT_TENANT_NAME=默认租户
```

可选值：

```text
SINGLE   单租户运行模式
MULTI    多租户运行模式
```

生产环境必须由受控配置中心或部署密钥注入，禁止通过 URL、Cookie、普通数据库字段或前端 localStorage 控制。模式变更必须经过变更审批、双人复核、备份、演练和回滚准备。

### 4.2 单租户模式

单租户模式要求：

1. 数据库中仍然存在一个真实的 `ACTIVE` 租户。
2. 所有有效用户必须绑定该租户。
3. 新增用户由服务端自动绑定默认租户。
4. 前端不能提交或修改 `tenantId`。
5. 所有查询继续使用 `tenantId = currentTenantId`。
6. 租户选择接口仍可复用，但只能返回并接受该唯一租户，不能借此扩大数据范围。
7. 文件、审批、缓存 Key、任务和审计记录仍携带租户 ID。
8. 默认租户不存在、重复、禁用或配置不一致时，应用拒绝启动或进入只读维护状态。

单租户模式只是把可用租户集合限制为一个，不能使用 `tenantId IS NULL` 代表公共数据，也不能在代码中删除租户条件。

### 4.3 多租户模式

多租户模式要求：

1. 用户通过成员关系绑定一个或多个租户。
2. 每个租户拥有独立的组织树、角色绑定、数据范围、配额和策略版本。
3. 登录后必须有一个服务端确认的当前租户。
4. 用户只能切换到有效成员关系允许的租户。
5. 切换后重新加载角色、数据范围、字段权限和风险策略。
6. 跨租户资源 ID、文件 ID、审批 ID 和任务 ID 不得直接复用为授权凭据。
7. 平台管理员权限和租户业务权限分层，平台管理员不自动获得租户业务数据下载权。

## 5. 推荐数据模型

系统必须以成员关系和会话上下文作为租户授权的唯一事实源。用户表上的租户/组织/部门字段不得作为授权回退依据；如果保留为查询冗余字段，必须由服务端事务维护，禁止客户端写入。

### 5.1 租户

```text
sys_tenant
- id
- code                  UNIQUE
- name
- status
- security_policy_version
- data_scope_version
- created_at
- updated_at
- disabled_at
```

### 5.2 用户成员关系

为支持未来一个用户加入多个租户，新增：

```text
sys_user_tenant
- id
- user_id
- tenant_id
- status                ACTIVE / SUSPENDED / EXPIRED / REVOKED
- default_tenant       BOOLEAN
- valid_from
- expires_at
- assigned_by
- assigned_at
- revoked_by
- revoked_at

实现中的成员关系表为 `sys_user_tenant_membership`，并使用 `(user_id, tenant_id)` 唯一约束、状态和有效期索引。所有新用户创建必须在同一事务中创建 ACTIVE 成员关系。

### 5.3 会话当前租户

```text
sys_session.active_tenant_id -> sys_tenant.id
```

认证会话创建时由服务端从 ACTIVE 成员关系选择默认租户；每次请求重新校验会话租户、租户状态和成员关系。切换接口为：

```text
GET  /api/v1/auth/tenants
POST /api/v1/auth/tenant { "tenantId": "..." }
```

`POST /auth/tenant` 只更新当前会话，不改变用户成员关系；单租户模式最多返回一个租户，多租户模式返回该用户的 ACTIVE 成员关系集合。没有成员关系、租户不是 ACTIVE 或会话租户为空时拒绝请求。
- revoke_reason
- version
```

唯一约束：

```text
UNIQUE(user_id, tenant_id)
```

一个用户最多只能有一个有效默认租户。成员关系必须带审计和版本号，不能由普通用户直接修改。

用户表中的租户字段不参与授权判定；部署切换必须完成成员关系初始化后才允许启用新模式。

### 5.3 组织与部门约束

```text
sys_organization
- id
- tenant_id NOT NULL
- parent_id
- code
- name
- status

sys_department
- id
- tenant_id NOT NULL
- organization_id NOT NULL
- parent_id
- code
- name
- status
```

必须有数据库和服务端双重约束：

- `organization.tenant_id` 必须有效且 ACTIVE；
- `department.tenant_id` 必须与 `organization.tenant_id` 相同；
- `department.organization_id` 必须属于同一租户；
- 父组织、父部门必须属于同一租户；
- 不允许形成层级环；
- 用户的租户、组织、部门必须一致；
- 组织或部门禁用前必须检查有效子节点、用户、角色范围和业务数据。

### 5.4 会话上下文

多租户模式下，会话或服务端 Session 至少保存：

```text
userId
activeTenantId
membershipId
sessionVersion
roleVersion
dataScopeVersion
securityProofVersion
```

不建议只把租户 ID 放在 JWT 而不支持撤销。若使用短期 JWT，必须通过 Session 版本、成员关系版本和租户策略版本校验；高风险操作必须重新认证或 MFA。

## 6. 用户、组织和部门生命周期

### 6.1 新增用户

单租户模式：

```text
服务端读取默认租户
→ 校验租户 ACTIVE
→ 创建用户和租户归属
→ 可选绑定组织、部门
→ 写入审计
```

多租户模式：

```text
创建用户主体
→ 创建者选择目标租户
→ 校验创建者对目标租户的管理权限
→ 创建用户成员关系
→ 校验组织/部门属于目标租户
→ 写入用户、成员、归属和审计
```

创建请求不得直接接受以下字段作为最终值：

```text
tenantId
organizationId
departmentId
roleIds
permissionIds
status
roleType
```

这些字段即使存在于内部 DTO，也必须经过专用接口、数据范围和审批流程处理。

### 6.2 用户归属变更

改变用户租户、组织或部门属于高风险操作：

1. 校验操作者当前租户和管理权限；
2. 校验目标租户、组织、部门均 ACTIVE；
3. 检查用户现有角色和数据范围是否需要撤销；
4. 检查未完成审批、文件任务、下载凭证和业务绑定；
5. 需要时执行申请、审批、执行、复核四阶段；
6. 使旧 Session、旧安全证明和旧下载 URL 失效；
7. 写入前后快照、操作者、原因和审计完整性哈希。

### 6.3 组织和部门移动

组织或部门树移动必须在事务中完成：

- 锁定源节点、目标节点和租户；
- 检查目标节点属于同一租户；
- 检查不会形成环；
- 重新计算受影响用户的数据范围；
- 使相关权限缓存失效；
- 对跨组织、跨部门移动执行审批和双人复核。

## 7. 认证、租户选择和切换

### 7.1 登录

登录只证明用户身份，不自动证明用户有权访问所有租户。登录流程：

```text
凭证验证
→ 账户状态检查
→ MFA/风险策略
→ 查询有效成员关系
→ SINGLE：绑定唯一默认租户
→ MULTI：选择默认租户或进入租户选择页
→ 创建带租户上下文的 Session
```

没有有效成员关系时拒绝进入业务系统；不能回退到空租户、全租户或“平台默认数据”。

### 7.2 租户切换

建议接口：

```http
POST /api/v1/session/tenant
Content-Type: application/json

{
  "tenantId": "target-tenant-uuid"
}
```

服务端处理：

1. 从当前登录 Session 获取用户身份；
2. 查询目标成员关系，不能只查询目标租户；
3. 校验成员关系、租户和账号均 ACTIVE；
4. 检查租户策略是否要求重新认证或 MFA；
5. 原子更新 Session 的 `activeTenantId`、`membershipId` 和版本号；
6. 清理旧租户权限缓存、下载凭证和前端状态；
7. 重新加载角色、字段权限、数据范围和风险策略；
8. 写入成功或失败审计。

切换失败必须返回统一错误，不泄露目标租户是否存在。租户切换不能通过 GET 完成，也不能只依赖客户端 Cookie 中的租户 ID。

### 7.3 高风险切换

下列情形必须重新认证并要求 MFA：

- 切换到包含系统、安全、审计或平台管理权限的租户；
- 切换后访问文件、审计、审批或密级数据；
- 近期发生密码、MFA、成员关系或角色变更；
- 登录风险、IP、设备或地理位置发生异常变化。

## 8. 授权与数据范围模型

### 8.1 授权决策顺序

所有业务接口必须按以下顺序拒绝优先：

```text
认证有效？
→ 当前租户有效？
→ 用户是该租户成员？
→ 接口权限有效？
→ 组织/部门/自定义数据范围有效？
→ 目标资源属于当前租户？
→ 字段权限允许？
→ 风险证明、MFA、审批满足？
→ 执行最小化查询
```

任何一步无法确定都拒绝，不能使用“查不到权限就按全部数据”或“系统管理员自动放行”的兜底逻辑。

### 8.2 数据范围

推荐范围：

```text
SELF
DEPARTMENT_SELF
DEPARTMENT_TREE
ORGANIZATION_SELF
ORGANIZATION_TREE
TENANT
CUSTOM
```

每个范围都必须先加入租户条件：

```text
tenantId = session.activeTenantId
AND scopePredicate
```

`CUSTOM` 必须经过审批、有效期、目标校验和双人复核。部门树和组织树必须防环，并在结构变更后使范围缓存失效。

### 8.3 管理员边界

平台管理员可以管理租户、成员关系和安全策略，但不因拥有平台管理权限自动获得业务文件下载、业务对象查看或跨租户导出权限。

系统管理员、业务管理员、安全管理员、审计管理员职责分离：

- 申请人不能审批自己的申请；
- 审批人不能执行自己的申请；
- 复核人不能与申请、审批、执行人员重复；
- L3 操作要求 MFA、重新认证、审批、双人控制和完整审计。

## 9. 文件模块隔离要求

文件模块必须绑定：

```text
file.tenantId
file.ownerUserId
owner.organizationId
owner.departmentId
file.binding.resourceType
file.binding.resourceId
```

文件上传会话、分片、最终化任务、扫描任务、审批、绑定和对象存储路径都必须通过文件对象和租户边界关联。

### 9.1 单租户模式

- 上传会话自动使用当前默认租户；
- 业务列表只查询当前用户范围；
- 系统文件管理只查询默认租户；
- 不提供租户切换；
- `READY + CLEAN` 之外的文件不能下载、绑定或业务使用。

### 9.2 多租户模式

- 上传会话绑定 Session 中的当前租户和用户成员关系；
- `uploadId`、`fileId` 不能代替登录态和租户校验；
- 分片、完成、状态、下载、绑定和解绑均重新校验当前租户；
- 切换租户后旧租户上传会话不能继续写入；
- 对象存储 Key 不包含可预测用户文件名，不向前端返回物理路径或对象 Key；
- 文件下载 URL 绑定文件、租户、用户、权限版本和短期过期时间。

## 10. 缓存、队列和异步任务

所有缓存 Key 和任务载荷必须包含租户边界：

```text
authz:{tenantId}:{userId}:{roleVersion}
scope:{tenantId}:{userId}:{scopeVersion}
file-scan:{tenantId}:{fileId}:{jobId}
idempotency:{tenantId}:{userId}:{key}
```

禁止使用不含租户的通用 Key，例如：

```text
user:{userId}
file:{fileId}
permission:{userId}
```

Worker 执行任务前必须重新读取任务所属租户、文件所属租户和当前策略版本。旧租户任务、旧扫描结果和旧审批引用不能覆盖新任务结果。

## 11. 模式切换方案

### 11.1 SINGLE → MULTI

1. 冻结租户、组织、部门和成员关系写入；
2. 备份数据库、对象、任务、审批和审计；
3. 创建并启用 `sys_user_tenant`；
4. 按一次性迁移规则将现有有效租户关系转换为成员关系；
5. 补齐所有组织、部门、文件、绑定和任务的 `tenantId`；
6. 检查空租户、跨租户外键、重复成员和孤儿文件；
7. 为平台管理员建立独立平台权限，不复制业务下载权限；
8. 灰度启用 `MULTI`，先允许只读租户选择；
9. 验证跨租户拒绝、文件隔离、审计和恢复；
10. 通过审批后开放写入和租户切换。

切换前必须达到：

```text
tenantId 空值记录 = 0
跨租户组织/部门引用 = 0
跨租户文件绑定 = 0
无归属扫描/最终化任务 = 0
无归属审批和审计记录 = 0
```

### 11.2 MULTI → SINGLE

多租户回退比升级更危险，不能简单把模式改为 `SINGLE`。必须：

1. 选择唯一目标租户；
2. 冻结其他租户写入；
3. 导出、归档或按审批清理其他租户数据；
4. 处理用户多成员关系、组织部门、文件绑定、任务和审计；
5. 撤销非目标租户 Session、下载凭证、API Token 和审批引用；
6. 验证目标租户以外查询全部拒绝；
7. 备份并保留回滚窗口；
8. 变更配置并重启服务；
9. 完成复核后解除写冻结。

在数据未完成归档和隔离前，禁止切换为 `SINGLE`，否则会造成多租户数据被错误视为同一租户数据。

### 11.3 配置切换控制

模式配置变更必须具备：

- 变更单和风险评估；
- 双人审批和执行；
- 数据库、对象、配置和密钥备份；
- 演练记录和回滚脚本；
- 变更前后完整性校验；
- 应用重启或受控发布；
- 变更审计和复核。

## 12. 失败安全与回滚

### 12.1 启动检查

应用启动时检查：

1. `TENANCY_MODE` 合法；
2. SINGLE 模式默认租户唯一且 ACTIVE；
3. MULTI 模式成员关系表和索引存在；
4. 租户、组织、部门无跨租户引用；
5. 关键资源不允许存在空租户；
6. 审计完整性密钥和数据库连接有效。

检查失败时，应用不得自动降级到全量模式。

### 12.2 请求失败

- 没有当前租户：拒绝；
- 租户禁用：拒绝；
- 成员关系过期：拒绝；
- 组织部门不匹配：拒绝；
- 权限缓存版本过期：重新加载，加载失败则拒绝；
- 审计写入失败：高风险操作拒绝完成；
- 文件扫描不确定：保持隔离，不得放行。

### 12.3 回滚

回滚只能恢复到已验证的数据库、对象、配置和密钥快照。不得使用 `git reset`、直接删除租户数据或手工修改状态绕过审批。恢复后必须重新校验：

```text
租户归属
组织部门层级
用户成员关系
角色和数据范围
文件哈希和安全状态
审批链
审计完整性
```

## 13. 审计与监控

至少记录：

- 租户创建、禁用、恢复和删除申请；
- 用户加入、退出和切换租户；
- 组织、部门创建、移动、合并和删除；
- 角色、数据范围和字段权限变更；
- 模式配置变更和发布；
- 跨租户访问拒绝；
- 文件上传、扫描、下载拒绝、绑定和解绑；
- 任务重试、死信和恢复；
- 数据修复、备份恢复和回滚。

审计记录至少包含：

```text
eventId, traceId, time, actor, tenantId, membershipId
organizationId, departmentId, action, targetType, targetId
result, riskLevel, requestId, sourceIp, userAgent
policyVersion, beforeSnapshot, afterSnapshot, reason
```

不得记录密码、OTP、Cookie、Token、文件原文、对象完整 URL、ClamAV 协议原文和内部堆栈。

监控指标至少包括：

- 空租户请求数；
- 跨租户访问拒绝数；
- 租户切换失败数；
- 组织部门循环检测失败数；
- 成员关系异常变更；
- 文件扫描积压、超时和死信；
- 权限缓存版本不一致；
- 审计写入失败；
- 租户数据迁移校验失败；
- 孤儿对象和孤儿元数据。

## 14. 等保和高安全控制映射

| 控制域 | 本方案控制措施 | 验收证据 |
| --- | --- | --- |
| 身份鉴别 | 登录、Session 版本、重新认证、MFA、成员关系校验 | 登录日志、MFA 记录、Session 撤销记录 |
| 访问控制 | RBAC + 租户边界 + 组织部门数据范围 + 字段裁剪 | 权限矩阵、越权测试、策略版本 |
| 安全审计 | 租户、成员、切换、组织、文件和模式变更全量审计 | 审计日志、完整性校验、复核记录 |
| 入侵防范 | 限流、幂等、防重放、失败锁定、异常告警 | 防护配置、告警记录、攻击测试 |
| 数据完整性 | 事务、版本号、哈希、任务幂等、孤儿检测 | 校验报告、恢复演练 |
| 数据保密性 | HTTPS、私有存储、短期下载凭证、最小字段返回 | TLS 配置、对象存储策略、接口响应 |

| 供应链和运维 | 配置审批、双人复核、密钥管理、变更回滚 | 变更单、发布记录、密钥轮换记录 |

## 15. 实施顺序

### 阶段一：单租户安全基线

1. 初始化唯一默认租户；
2. 所有初始化用户绑定默认租户；
3. 新增用户服务端自动绑定租户；
4. 文件、用户、组织和部门查询强制租户过滤；
5. 删除所有从用户固定租户字段、空租户或平台默认租户推断授权范围的兜底逻辑；
6. 增加启动检查和租户边界测试。

### 阶段二：组织部门闭环

1. 完善组织和部门管理接口；
2. 加入同租户、父子关系和防环校验；
3. 用户创建和归属变更接入组织部门校验；
4. 数据范围支持部门和组织树；
5. 增加结构变更审批和审计。

### 阶段三：多租户数据模型

1. 新增用户-租户成员关系表；
2. 为每个有效用户建立唯一的初始 ACTIVE 成员关系；
3. 将角色、数据范围、文件、审批和任务补齐租户关联；
4. 建立租户级缓存 Key 和任务载荷；
5. 完成跨租户静态分析、数据扫描和恢复演练。

### 阶段四：多租户切换

1. 增加租户选择和切换接口；
2. 引入重新认证、MFA 和 Session 版本刷新；
3. 灰度开放只读切换；
4. 完成跨租户安全测试；
5. 审批后开放写入和高风险操作。

## 16. 验收清单

### 租户隔离

- [ ] 用户不能读取其他租户用户、组织、部门和文件；
- [ ] 篡改 `tenantId`、`organizationId`、`departmentId` 无效；
- [ ] 构造其他租户的资源 ID 返回统一拒绝或不存在；
- [ ] 禁用租户所有业务请求默认拒绝；
- [ ] 空租户数据不被全量查询；
- [ ] 管理员不能因平台权限自动下载业务文件。

### 模式切换

- [ ] SINGLE 模式不存在租户切换接口放行；
- [ ] MULTI 模式只能切换到有效成员关系租户；
- [ ] 切换后角色、范围、字段权限和缓存全部刷新；
- [ ] 模式变更有审批、备份、双人复核和回滚记录；
- [ ] SINGLE → MULTI 和 MULTI → SINGLE 均完成数据校验。

### 组织部门

- [ ] 不能跨租户挂载组织、部门或父节点；
- [ ] 不能形成组织或部门循环；
- [ ] 部门树、组织树数据范围边界正确；
- [ ] 移动、合并和删除会失效权限缓存并记录审计；
- [ ] 用户归属变化后旧会话和旧下载凭证失效。

### 文件和异步任务

- [ ] 非 `READY + CLEAN` 文件不能下载、绑定或使用；
- [ ] 上传会话和任务不能跨租户操作；
- [ ] 扫描服务不可用时文件保持隔离；
- [ ] 任务租约、重试、死信和重启恢复有效；
- [ ] 文件哈希、任务 ID、租户和审计链可关联。

## 17. 设计结论

推荐先以 `SINGLE` 模式上线，但从第一天就使用真实租户、组织、部门和服务端数据范围。未来切换 `MULTI` 时，只增加成员关系和租户切换能力，不改变文件、权限和审计的安全原则。

最重要的不可妥协规则是：

```text
没有有效租户上下文，不查询业务数据；
没有有效成员关系，不切换租户；
没有服务端数据范围，不执行操作；
没有 CLEAN + READY，不使用文件；
没有审批、复核和审计，不执行高风险变更。
```
